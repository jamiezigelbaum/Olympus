# Filing: where things go

Ask these questions in order:

1. Does it have a finish line the owner committed to? It is a project.
2. Is it an enduring responsibility with an evidenced standard? It is an area.
3. Is it a person, organization, topic, or reference? Wiki authoring is out of
   scope for this version; leave a pointer in Context instead of building a
   wiki page.
4. Is it done or dead? Archive its project state. Move enduring records to the
   area or entity that now owns them.

People are entries, not areas. A domain of interest is a topic/resource, not an
area. A project that becomes one action can become a task on the configured
authoritative task surface. A someday project gets a hub line, not an empty
page. Name work by what it is in the owner's world, never by provider labels or
message subjects. (Rule: `lazy-materialization`)

## Trust filing

Classify the item by content. Its source family—email, messages, files, or
anything else—does not determine whether it is restricted. (Rule:
`restricted-by-classification`)

When content is classified restricted:

- use the configured surface's restricted marker when it has one;
- on Reflect, the adapter mapping is `private: true`;
- when the surface has no restricted marker, omit the unsupported marker and do
  not write secure detail to an unprotected page;
- keep credentials, account numbers, and raw sensitive documents out of PKM
  pages even when the page is restricted; link to their approved location and
  retain only the useful, policy-allowed summary.

## Registry

Use the per-install project/area registry through the configured writable PKM
surface. Its location, edit protocol, and protection mechanism are installation
settings. Read it before filing, and propose changes through the authorized
surface without silently rewriting owner data.
